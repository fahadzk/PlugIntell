## Application and HTTP checks

Workspace smoke programs under `target/` exercised the actual packaged applications:

- Studio API generation, asynchronous Maven jobs, ZIP download and extraction, then `java -jar` from the extracted project directory. Relative `lib/` resolution passed.
- Minimal CLI output excludes web/Kafka libraries and monitor assets and does not expose `serve`.
- A web-enabled ZIP served its pinned imported declarative template and trusted bridge, completed two independent ingestion runs, and returned topology, safe summaries, run history and 30 contiguous unique-ID SSE envelopes. Studio pipeline/plugin/provider control endpoints returned 404 on the generated host.
- The Java generator's tests compiled and ran ingestion and query lanes with independent configuration, including a reporting constructor on a custom plugin outside the built-in namespace.
- A generated JVM web application completed a query using an offline plugin with Ollama's `AnswerResult` output contract. Its no-store result endpoint returned the actual answer and source/page citations, while snapshots, history and structured logs excluded the answer and retrieved document text. This did not call a live Ollama provider. Frontend regressions cover safe text rendering, historical results, late responses after run selection changes, request retries and keeping answer content out of custom-template messages.
- The Python-generated web application was compiled with the actual selected JARs and ran a real Micronaut host using the Water template. Its four-stage ingestion run succeeded with structured progress. This check used `javac` and the generated resources, rather than an installed-artifact Maven build.
- Authenticated HTTP tests published/executed ingestion as an administrator, read snapshots as a viewer, and resumed viewer SSE after `Last-Event-ID: 2` at sequence 3. Anonymous access was rejected; viewer/operator project builds and template imports were rejected; an editor reached build validation.
- A committed filtered Studio trace survived backend restart. Hidden domain progress was removed, authoritative lifecycle state and safe summaries survived, duplicate replay was ignored, and cursor replay/gap recovery passed.
- Declarative imports, executable-template trust rejection/acceptance, digest pins, archive validation and resource CSP/sandbox headers passed. No test renders plugin strings as HTML.
- A real Windows junction ancestor was rejected with HTTP 400 without writing a generated project through it. Absolute/nonempty destination and loopback/role restrictions also passed their backend tests.
- Standard, Water and declarative renderers preserve reported partial counts on success. Missing/unknown totals show completion status without a fabricated percentage or tank level.
- All ten runtime assets, including the new Studio template helper, matched frozen/source, packaged API JAR and HTTP bytes after the final UI revision.
- Updated generated READMEs and startup scripts list `serve` only for web-enabled output. A fresh exported CLI project ran through `run.bat` from another working directory with a spaced input filename, and propagated a Java failure exit code. Two exported web runs produced startup, run/node/attempt/progress/completion logs in both console and `logs/server-0.log`; direct plugin stdout remained visible in the console. The Python-generated web host was also compiled and executed with structured file logs.

The smoke chains use synthetic text and built-in extract/split/test-embedding/test-writing plugins. They do not contact external providers or use user documents. See [usage and protocol](events-and-generated-apps.md) for startup, generation and template instructions.

## Native and external checks

A downloaded CLI bundle was compiled directly with GraalVM Native Image and Visual Studio's x64 toolchain. Its resulting Windows executable successfully ingested the synthetic sample and confirmed one stored chunk. The tested chain was `ExtractTextPlugin -> StaticSplitterPlugin -> TestEmbedderPlugin -> TestWriterPlugin`. This verifies that limited native scope, not every provider or OCR dependency.

A generated Micronaut/Local UI web project was built with Native Build Tools 0.10.6, GraalVM CE 21.0.2 and the Windows x64 C++ toolchain, using `mvn -B -o -Dmaven.repo.local=D:/Work/Main/.m2/repository -Pnative -DquickBuild=true package` from the exported fixture folder. The quick-build executable was then checked with `python tools/verify_native_web.py target/native-web-executable-smoke`. This check copied only the executable and native startup script to a folder containing spaces, set JAVA_HOME to an absent installation and removed Java from PATH. UI assets, ingestion, two independent queries, actual answer/citation metadata, snapshots/history, SSE cursor replay/history gaps, input-path rejection, console/file logs and native batch help/exit codes passed. It uses offline `IngestFixture`/`AnswerFixture` providers, not live Ollama or Neo4j. The generated application's processing/adapter assembly remains explicit; Micronaut retains its normal compiled bean infrastructure.

Studio's asynchronous native build was then exercised through HTTP with those two fixture plugins and a fresh SQLite database. It generated the published Micronaut/Local UI project, ran Maven with `GRAALVM_QUICK_BUILD=true`, reached `SUCCEEDED`, and exposed both the native artifact and ZIP. Their executable bytes matched by SHA-256. The ZIP was extracted and its executable passed the same isolated runtime checks, including query answers, SSE and logs. The workspace report is `target/native-project-api-2acb22e1/report.json`. All verification servers and compiler processes created by these scripts were stopped or exited; existing user servers were left running.

The external-template smoke run repeated this flow with an edited/imported Aurora starter, typed settings and an extra SVG resource. The native build used the repaired installed SDK launcher without the earlier location override. It bundled only the selected imported view, served its manifest/HTML/CSS with sandbox headers, and passed ingestion, two queries, answer/citation output, SSE replay/gaps, input validation, history, logging and native batch checks from an isolated folder without Java or external JARs. The executable and ZIP downloads matched by hash. The report is `target/external-template-api-ac23886b/report.json`; `python tools/verify_native_web.py target/external-template-api-ac23886b/extracted/NativeWeb` additionally fetched the declared SVG asset successfully. These runs used offline fixture providers, not live Ollama/Neo4j services. See [Local UI templates](ui-templates.md) for configuration and the supported protocol.

The first native compile exposed Netty 4.2.5 initialization conflicts. Web-only `--initialize-at-run-time=io.netty,org.slf4j` resolved them; native CLI projects do not receive that argument. The optional host's Graal processor is confined to annotation processing, and resource metadata includes the bundled UI/template tree. Initial failed compiles are not counted as passes. A Windows temp-file cleanup race in the generated JVM integration test was fixed with a bounded deletion retry after the owned server exited; the subsequent full reactor run passed.

Native Build Tools 0.10.6 and the Micronaut Graal processor were available in the cache for these checks. Earlier native checks supplied `location=<GraalVM>/bin/` only to their child environment because the installed SDK wrapper had its location assignment commented out. The user restored `call :getScriptLocation location`, and a fresh `native-image --version` subsequently passed without that environment override. No installed SDK files were changed by the agent. The native executable itself requires neither a workaround nor Java.

`mvn -o -Pkafka -pl pipeline-event-kafka -am compile -DskipTests` failed because `org.apache.kafka:kafka-clients:4.0.0` is absent from the cache. Consequently the enabled producer sources, MockProducer tests, generated Kafka combinations and broker integration were **not verified**. The default distribution explicitly reports Kafka unavailable. On a network-enabled machine, build/install with `mvn -Pkafka clean install`; broker testing additionally requires `PLUGINTELL_KAFKA_TEST_BOOTSTRAP` as described in the usage guide. Do not count an unavailable broker or disabled-producer build as a Kafka integration pass.

Two isolated headless Edge attempts crashed before page interaction with access-denied GPU-process errors. Rendered layout, browser interaction, animations and browser enforcement of iframe CSP remain unverified. DOM behavior, source/JAR/HTTP assets and response headers were checked separately.

Live Neo4j/Ollama services and provider/OCR document execution were not validated here. Native Micronaut/Local UI hosting was verified on Windows with offline providers; the real selected provider libraries were additionally compiled as described below. Other native OS/toolchain combinations were not executed. Kafka native generation remains unsupported. Python generator tests verify native profile/settings/script generation; native executable checks use the Java Studio generator. Telemetry remains best effort: bounded queues and shutdown can lose events, standalone history is volatile, and Studio preserves committed SQLite rows but can lose pending buffered telemetry.

## Real provider native dependency regression

A Studio-generated two-workflow project containing document-splitter-lang4j, Ollama embedding/answer, Neo4j writer/retrieval, Micronaut and Local UI originally failed with `CleanerJava6Substitution.CLEANER_FIELD_OFFSET`. Its provider JARs embedded Netty 4.1.119 while the web host embedded 4.2.5. The reactor now shares Netty 4.2.5 dependency management; generated Python web POMs use the same BOM. Studio rejects incompatible embedded Netty artifact versions. Forced recreation of unshaded inputs prevents stale classes surviving repeated shade/package runs.

The next compile identified missing Jakarta Mail signatures during Angus activation analysis. The Tika-backed splitter now bundles the Mail API, with a regression test that inspects its mailcap handler signatures. Neither native feature nor cleanup logic was disabled.

The repaired real project passed `mvn -B -o -Dmaven.repo.local=D:/Work/Main/.m2/repository -Pnative -DskipTests package` with the installed GraalVM CE 21.0.2 and MSVC toolchain. This was a normal optimization-level-2 build, not quick-build mode. The native build took 17m15s and emitted a 139.43 MB executable plus 11 DLL sidecars for document/image support. The complete Windows runtime ZIP preserves these beside the binary. Native help, invalid-mode exit status and batch help passed from a directory containing spaces, with Java removed from PATH and an invalid JAVA_HOME. The local report is the generated project's `target/native-distribution-verification.json`; build output is `target/native-mail-rebuild.log`.

The same repaired provider libraries served the JVM application's API successfully on a temporary port. A native HTTP startup attempt could not complete with the project's fixed port 8085 already occupied; that existing service was left running. This check does not claim real-provider native HTTP or live ingestion/query passed. Earlier offline-provider native HTTP/SSE/template checks remain separate evidence.

Two regression attempts during native compilation encountered generated-JVM startup/CLI timeouts; they were not counted as passes. The full 128-test reactor run passed after native compilation finished. Generated-process test cleanup now terminates its own timed-out children and uses bounded startup deadlines. The Windows symbolic-link limitation remains a skip.
